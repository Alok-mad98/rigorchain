# Rigor Consensus Formal Verification

> **Scope statement (read this first).**
> This directory contains a Python executable specification, a Coq corpus of 196
> machine-checked files, and test/fuzz tooling. It does **not** contain a proof
> that the C++ implementation matches the specification, and it does **not**
> contain a no-fork theorem. Equivalence between the three layers is **NOT
> ESTABLISHED**. Every claim below is accompanied by the file and line where it
> can be checked; if a claim here cannot be located in the source, treat the
> claim as a documentation bug and file it.

**Authority rule** (see `docs/proof/PROOF034_CANONICAL_AUTHORITY.md`): when this
document conflicts with the code, **the code wins**. This README was rewritten
under SECURITY-001-F to remove claims that the code does not support.

---

## 1. The three layers, and what actually connects them

| Layer | Artifact | Status |
|---|---|---|
| L1 — Executable spec | `spec/rigor_consensus_spec.py` | Single source of truth (SSOT). Normative. |
| L2 — Coq model | `coq/**` (196 files) | Machine-checked. Independently re-derives L1 byte semantics. |
| L3 — C++ production | `core/src/**` | Validated against L1 by golden vectors and harnesses, **not** by proof. |

Connections that actually exist:

- **L1 ↔ L2**: 25 golden vectors are recomputed *inside the Coq kernel* and
  checked against the Python-produced expected bytes — `coq/Kernel/GoldenHarness.v`
  (25 enforced lemmas; the file is generated by `gen_coq_harness.py` from L1 data).
  This is the strongest cross-layer evidence in the repository. It is
  *vector-level* agreement on 25 inputs, not universally quantified equivalence.
- **L1 ↔ L3**: golden-vector fixtures and runtime harnesses under
  `core/src/proof/`. Note the harness JSON deliberately carries
  `equivalence_claimed: false`.
- **L2 ↔ L3**: **nothing.** There is no extraction, no refinement proof, and no
  verified compilation path. This is tracked as open proof debt PD-4F-CPP-01 and
  PD-4F-OB-02.

There is **no** theorem anywhere in `coq/` of the form "C++ = Python = Coq".
Any document asserting one is wrong.

## 2. What is actually proven in Coq

All results below are `Qed` and were located by file+line in the current tree.
Two global caveats apply and are stated once here:

- **Declared axioms.** The corpus declares exactly two: `Parameter hash256 : Z -> Z`
  (`coq/Hash.v:5`) and `Axiom hash256_deterministic` (`coq/Hash.v:7`). `Hash.v` is
  imported only by `coq/Extraction.v:6`, and the assumption scan confirms **no
  top-level result depends on either** — see §5. The byte-level modules
  (`RigorSha256.v`, `RigorHash.v`, `Kernel/*`) compute real SHA-256 on real bytes
  and use no parameters.
- **Model-vs-implementation caveat.** Every theorem is about the Coq model. It
  transfers to production only insofar as the model matches `core/src/**`, which
  is unproven (see §4).

### 2.1 Byte-exact SHA-256 and golden vectors (strongest artifact)

- `coq/RigorSha256.v` — executable SHA-256 over `list byte`, no parameters.
- `coq/RigorHash.v:9` — `hash256_bytes` = SHA256d at byte granularity.
- `coq/Kernel/GoldenHarness.v` — 25 golden vectors (ConvergenceRoot, PCORB hash,
  eligibility, winner selection) recomputed by `vm_compute` in the Coq kernel and
  proven equal to the L1-produced expected bytes. Each vector is a `Lemma
  golden_<ID> : chk_<n> = true` closed with `vm_cast_no_check (eq_refl true)`,
  so **a regressed vector breaks the build**. This file is listed in `_CoqProject`
  as of SECURITY-001-F; before that it was never compiled.

### 2.2 Determinism

- `coq/Proofs/Determinism.v:7` — `selection_deterministic`: `Execute` yields at
  most one winner for given inputs.
- `coq/Phase4FConsensus/ConsensusDeterminism.v:12` — `execute_transition_deterministic`.
- `coq/Phase4FConsensus/ConsensusDeterminism.v:27` — `execute_trace_deterministic`
  (previously `Admitted`; discharged under SECURITY-001-F).
- `coq/Phase4FConsensus/ConsensusDeterminism.v:50` — `consensus_replay_determinism`:
  replaying the same trace from the same state yields the same state.
- `coq/ReplayReorgCore/SupplyConservation.v:222` — `supply_deterministic`.

Note the scope: these say the transition *function* is a function. They do not
say two nodes given *different but equivalent* block encodings agree; that is the
order-independence gap in §4.

### 2.3 Selection and ordering

- `coq/Kernel/KernelSelection.v:32` — `pick_better_tx_prefers_lower`.
- `coq/Kernel/KernelSelection.v:41` — `pick_better_tx_tie_txid` (tie-break is by txid bytes).
- `coq/Kernel/KernelSelection.v:52` — `select_winner_in`: the winner is a member of the input set.
- `coq/Kernel/KernelSelection.v:70` — `select_winner_none_nil`.
- `coq/RigorBytesOrder.v:26,46,69` — `bytes_ltb_trans`, `bytes_ltb_antisym`,
  `bytes_ltb_total`: the memcmp byte order is a strict total order.
  (`nat_ltb_false_gt` at line 13 was `Admitted`; discharged under SECURITY-001-F.)
- `coq/Kernel/KernelRoot.v:21,32,50` — `converge_root_length`,
  `converge_root_small` (fewer than 2 txids ⇒ 32 zero bytes), `converge_root_large`.

### 2.4 UTXO and replay/reorg

- `coq/ReplayReorgCore/ReplayInvariants.v:205` — `utxo_spend_removes_output`,
  **now with a `not_recreated` side condition**. See the warning in §3.
- `coq/ReplayReorgCore/ReplayInvariants.v:190` —
  `utxo_spend_removes_output_unconditional_is_false`: a machine-checked
  *refutation* of the unconditional form.
- `coq/ReplayReorgCore/ReplayInvariants.v:230` — `rollback_restores_previous_state`.
- `coq/ReplayReorgCore/ReplayInvariants.v:256` — `replay_preserves_utxo_consistency`
  (same side condition).
- `coq/ReplayReorgCore/SupplyConservation.v:245,311,411` — `supply_monotonic`,
  `rollback_preserves_supply`, `genesis_supply_zero`.

### 2.5 Weak-but-honest results (self-labelled in source)

- `coq/Proofs/Safety.v:11` — `unique_mint`. The source comment at lines 7-10
  self-labels this **"WEAK (real, but content-light)"**: it proves `Execute` is a
  function, *not* supply-level mint uniqueness. Do not cite it as a supply guarantee.
- `coq/Proofs/Fairness.v:16,25` and `coq/Proofs/SplitInvariance.v:13` — real
  deterministic selection/weight-conservation lemmas that **replace** earlier
  vacuous probabilistic statements. The probabilistic versions remain OPEN.
- `coq/Phase4GRefinement/FormalVerificationCertification.v:11-21` — an explicit
  **HONESTY BOUNDARY** section. It states that "READY_FOR_RELEASE" means the
  artifact set is consolidated and machine-checked, and explicitly **does not**
  mean Coq = Runtime, Coq = C++, or Coq = Consensus. The frozen verdict is
  `RV_Partial`, not `RV_Equivalent`. Preserve this text.

## 3. Known-false and explicitly-open statements

These are recorded here so nobody re-derives a false claim from an old document.

**A spent outpoint is *not* unconditionally removed in the current model.**
`apply_tx_utxo` assigns each created output the synthetic outpoint
`MkOutPoint hash32_placeholder (tx_index + i)`, which can collide with an
outpoint the same transaction spends. The unconditional lemma is therefore
refutable, and the refutation is checked by the build
(`coq/ReplayReorgCore/ReplayInvariants.v:190`). The usable theorem carries the
`not_recreated` precondition (`:137`). **This is a modelling defect, not a
production double-spend**: production uses real 32-byte txids, not a placeholder.
It is logged in the gap register because it means the model cannot currently
express the double-spend property in its natural form.

**Open proof obligations (unchanged, restated):** PD-4F-OB-02 (oracle agreement /
C++ bridge), PD-4F-CPP-01 (C++ equivalence), PD-4F-OB-03. Under SECURITY-001-F the
former `True`-bodied placeholder theorems in `ConsensusDeterminism.v:69`,
`ConsensusOracleBridge.v`, and `ConsensusTraceExecution.v` were replaced by
explicit `Prop` definitions naming the obligation plus a provable conditional
theorem, so the obligation is now visible in the source rather than disguised as
a discharged result.

## 4. Verification gap register (summary)

Full, prioritized register: `docs/security/TASK_SECURITY_001_F_REPORT.md`.

| # | Gap | Why it matters |
|---|---|---|
| G-1 | **No transaction-order independence.** `Permutation` appears **zero times** in all 196 Coq files. | The anti-fork argument depends on it. Two nodes that order the same tx set differently are not proven to agree. |
| G-2 | **No supply cap.** `cb_oru_subsidy` is read from the attacker-supplied block and `valid_block_connect` does not bound it. | Unbounded issuance is representable in the model; the model cannot rule out inflation. |
| G-3 | **No Coq↔C++ equivalence.** No extraction, no refinement. | All Coq results are about the model only. |
| G-4 | **Vector-level, not universal, L1↔L2 agreement.** 25 inputs. | Sound but narrow. |
| G-5 | **Synthetic-outpoint collision** in the replay model (§3). | Double-spend prevention is not statable in its natural form. |

## 5. Building and running

### Coq corpus

```bash
cd formal_verification/coq
coq_makefile -f _CoqProject -o Makefile.coq
make -f Makefile.coq -j"$(nproc)"
```

`_CoqProject` lists all 196 `.v` files, including `Kernel/GoldenHarness.v`.
There is no `ArdaConsensus.v`; earlier revisions of this README told readers to
compile that file, and it has never existed.

### Assumption audit (what rests on axioms)

```bash
cd formal_verification
python3 tools/audit_assumptions.py
```

Runs `Print Assumptions` on every top-level `Theorem`/`Lemma`/`Corollary` and
emits the axiom-free vs axiom-dependent split. Run this before citing any
theorem as established.

### Python spec (L1)

```bash
cd formal_verification/spec
python3 rigor_consensus_spec.py
```

### Golden vectors

```bash
cd formal_verification/tests
python3 test_golden_vectors.py
```

A failing golden vector is a consensus-affecting regression.

### Differential fuzzer

```bash
cd formal_verification/fuzz
python3 differential_fuzzer.py
```

**Read the exit semantics before citing this tool.** Prior to SECURITY-001-F,
every `_call_cpp_*` and `_call_coq_*` hook returned the Python result, so the
comparison was `x == x` and could not fail. It has been rewritten to use a
genuinely independent **Coq oracle** (shells out to `coqc` and evaluates the Coq
model by `vm_compute`), and to report the C++ oracle as **UNAVAILABLE** unless
`RIGOR_CPP_HARNESS` points at a real harness binary. With no independent oracle
reachable the run now reports **INCONCLUSIVE**, not success. Do not cite a fuzzer
run as evidence unless its output names at least one independent oracle.

## 6. Byte-level requirements (normative, from L1)

These are requirements on implementations, not proven theorems.

- SHA256d exactly; no variants, no single-SHA.
- Height is LE64, previous target is LE32.
- txids sort by **memcmp byte order** — never numeric, never string-lexicographic.
- ConvergenceRoot is a **flat concatenation** of sorted txids then SHA256d — not a
  Merkle tree, and individual txids are not pre-hashed.
- Fewer than 2 eligible txids ⇒ ConvergenceRoot is 32 zero bytes
  (proven in the model: `coq/Kernel/KernelRoot.v:32`).
- Tie-break compares `txid XOR ConvergenceRoot` by memcmp.
- Inequality is strict: `H * COIN < T * W`.

Historical fork incidents motivating each rule (endianness, sort order, hash
variant, Merkle variant, tie-break ambiguity) are catalogued in the L1 spec
comments; they are context, not evidence about this codebase.

## 7. For auditors

1. Start with `spec/rigor_consensus_spec.py` — it is normative.
2. Run `tools/audit_assumptions.py` and read the axiom-dependent list first.
3. Check `coq/Kernel/GoldenHarness.v` — this is the load-bearing cross-layer artifact.
4. Read §3 and §4 before reading any other verification document in this repo.
5. Assume Coq↔C++ equivalence is **unproven** unless you find an extraction or
   refinement proof; as of this writing there is none.
