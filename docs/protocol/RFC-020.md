# RFC-020 — Deterministic Economics for Human and Machine Verification

## Continuous RES Destroy Cost, Flat ORU Emission

**Status:** Live issuance specification. **Issuance header + `GetBlockSubsidy`
landed.** Adoption record: `docs/economics/RFC-020-ADOPTION-STATUS.md`.
**Numeric SSOT:** `tools/res_continuous_price_schedule.py`. Every number in this
document is printed by that script, and every claim it makes is asserted there.
None was computed by hand.

```
equivalence_claimed = false
documentation_consensus_authority = false
refinement_proved = false
```

The RES destroy cost is a continuous function of the confirming block height.
The ORU block subsidy is 128 ORU for every height ≥ 1.

Convergence destroys ORU and may mint RES in the same body transaction.
The genesis destroy cost is 1024 ORU per RES — that is ORU destroyed to mint 1 RES
at height 0. The smallest destroy that mints one RES atom at height 0 is
1024 ORU atoms. Consensus evaluates the pole predicate, not a market quote.

---

## Overview

This section states a design goal. It is not a protocol rule. It does not change
a parameter, a formula, or any consensus description in this document.

One design goal of RIGOR is a deterministic economic system that humans and
machines can verify together.

Traditional economic models usually depend on human interpretation, market
expectations, governance adjustment, and external parameters. RIGOR states the
economic rules as deterministic mathematics, so any independent implementation
can recompute the economic state.

RFC-020 defines the RES issuance mechanism as an exact integer primitive.
Given block height, destroy amount, and the RES output, any implementation can
independently decide whether the issuance condition holds, how much RES that
destroy can produce, and what the future issuance trajectory is.

The goal is not for a machine to replace consensus. The rules are written so
that a wallet can calculate them, an explorer can check them, a third-party
tool can analyze them, and an AI agent can read and simulate them.

Machine-verifiable does not mean machine-controlled. A machine can verify the
rules. It cannot change them.

## 2. The rule

```
destroy_cost(h) = RES_DESTROY_COST_GENESIS · (2^25 + h)^2 / 2^50
```

Consensus never evaluates that expression. It evaluates the same relation with
the division cleared:

```
R > 0  →  R · (2^25 + h)^2 ≤ B << 40
R = 0  →  B unconstrained                   a plain destroy stays legal
```

where `R` is RES atoms minted, `B` is the ORU atoms in the single `OP_CONVERGE`
output, and `h` is the height of the confirming block.

The derivation is an identity in exact arithmetic, not an approximation:

```
R · destroy_cost(h)                        ≤ B · RES_COIN
R · 1024e8 · (2^25+h)^2 / 2^50      ≤ B · 1e8
R · 1024   · (2^25+h)^2             ≤ B · 2^50
R · 2^10   · (2^25+h)^2             ≤ B · 2^40 · 2^10
R          · (2^25+h)^2             ≤ B · 2^40
```

`RES_DESTROY_SHIFT = 50 − log2(1024) = 40` is therefore forced by the genesis
destroy cost, not chosen independently. Selecting a different genesis destroy
cost moves the shift and nothing else; `predicate_shift_is_exact` asserts the
relation.

Consensus evaluates one multiplication, one squaring and one shift.

**Overflow.** `R` is bounded by `RES_MAX_SUPPLY`, `B` by `MAX_MONEY`, `h` by
`INT32_MAX`. Worst case the left side reaches 2^110 and the right side 2^99,
against the `unsigned __int128` limit of 2^128. `no_overflow_in_uint128`
asserts both bounds.

**Rounding.** `check_mint` is exact, so there is no rounding direction to
specify. `destroy_cost(0)` is exactly 1024.

**No free mint is representable.** `destroy_cost(h)` is strictly positive at every
`h ≥ 0`, and `min_burn_for_one_atom(h) ≥ 1` everywhere.
`no_free_mint_anywhere` asserts it at nine probe heights including
`INT32_MAX`.

### 2.1 Termination

Minting ends when a whole block's subsidy no longer buys a single RES atom,
which the integer arithmetic decides:

```
height 118 599 277 598  =  year 2 254 957
```

This is a consequence of the parameters, not a parameter.

## 3. Emission

```
subsidy(0) = 0
subsidy(h) = 128 ORU        for every h ≥ 1
```

ORU supply grows arithmetically and its inflation rate decays as `1/t`: 1.00%
at year 100, 0.100% at year 1000, monotonically toward zero and never reaching
it.

ORU remains uncapped. Under `ρ = 100%` — every newly emitted ORU destroyed for RES
— total ORU supply is exactly constant. **ORU hardness is therefore endogenous:
it is a function of RES demand rather than of a declared schedule.** No fixed
cap can express that, which is the reason ORU does not get one.

`MAX_MONEY` (10^10 ORU) is crossed at year 1 485 under this subsidy. The bound
is an overflow sanity check rather than a supply cap; see §8.

## 4. Cap

`RES_MAX_SUPPLY` is not chosen. It is the closed-form integral of the per-block
mint ceiling:

```
RES_MAX_SUPPLY = Σ_{h≥0} S / destroy_cost(h)
               = (S / P0) · H
               = 2^7 / 2^10 · 2^25
               = 2^(7 − 10 + 25)
               = 2^22
               = 4 194 304 RES
               = 419 430 400 000 000 atoms
```

The exponent being exactly 2 is what makes the integral exactly `(S/P0)·H` with
no residual term, and therefore what makes the cap land *on* a power of two
rather than near one.

Cumulative issuance through any height also has a closed form, which removes the
need for any running counter in tooling:

```
cumulative(h) = RES_MAX_SUPPLY · h / (h + 2^25)
```

**Why this is an upper bound.** Total RES equals `Σ_h destroy(h)/destroy_cost(h)` subject
to `Σ_{h≤H} destroy(h) ≤ Σ_{h≤H} emitted(h)` for every `H`, since ORU cannot be
destroyed before it exists. `destroy_cost` is strictly increasing, so `1/destroy_cost` is
strictly decreasing, and by the standard exchange argument the sum is maximised
by destroying every ORU at the height it appears. That schedule is exactly the sum
above. `destroy_cost_strictly_increasing` asserts the premise.

The consequence is that **the cap needs no consensus enforcement**. Delaying a
destroy can only ever yield less RES, so no hoarding strategy reaches the bound
from above, and no cumulative counter has to be consulted during block
validation. RES-L2 remaining observational is correct rather than tolerated.

**Cap utilisation equals participation, exactly.** If a fraction `ρ` of emitted
ORU is ever destroyed for RES, realised issuance is `ρ · RES_MAX_SUPPLY`:

| ρ | Realised issuance | Utilisation |
|----:|------------------:|------------:|
| 5% | 209 715 RES | 5.0% |
| 20% | 838 861 RES | 20.0% |
| 50% | 2 097 152 RES | 50.0% |
| 100% | 4 194 304 RES | 100.0% |

## 5. Wallet construction

While minting is open, RES cannot trade above `destroy_cost(h)` ORU without offering a
riskless mint arbitrage. `destroy_cost(h)` is a protocol destroy requirement, not a
market quote. It is a hard ceiling on the RES/ORU ratio and a hard floor under ORU
denominated in RES.

The destroy cost changes by 0.000 089% per block. Wallets construct at the confirm
height plus a flat margin; the cost of an over-generous margin is a rounding error:

| Margin | Extra ORU paid |
|-------:|---------------:|
| 100 blocks | 0.000 596% |
| 1 000 blocks | 0.005 961% |
| 10 000 blocks | 0.059 614% |
| 100 000 blocks | 0.596 935% |

This repository's wallet takes that margin as 144 blocks after the current tip.
That constant is this wallet's construction choice. See
[Wallet Convergence confirmation margin](../wallet/WALLET_CONVERGENCE_HEIGHT_PAD.md).

There is no per-block mint cap, so one block may absorb an unbounded destroy.
The absence of rate limiting is deliberate.

## 6. Rejection codes

```
bad-txns-res-mint-underpaid        R · (2^25+h)^2 > B << 40
bad-txns-res-mint-no-burn          RES output present, no OP_CONVERGE output
bad-txns-res-mint-cap-overshoot    runtime defence; §4 makes it unreachable
bad-txns-res-amount-invalid        bad-txns-res-in-belowout
bad-txns-res-input-invalid         bad-txns-res-output-nonpositive
illegal-res-to-oru-conversion      bad-txns-spend-convergence
```

`bad-txns-res-mint-cap-overshoot` is a defensive check. A check that can never
fire is cheap; discovering that the derivation had a hole with no check in
place is not.

## 8. Out of scope

This RFC does not change PoW, ASERT, UTXO accounting, the script classifier,
serialization, P2P, `RES_MINT_MATURITY`, `MIN_CONVERGENCE_AMOUNT`, RFC-018's
half-fee destroy, or any genesis block.

It does not add a per-block mint rate limit. See §5.

It does not reduce RES supply sensitivity to participation. Lifetime issuance
still spans near zero to `RES_MAX_SUPPLY` depending on `ρ`. That is a property
of issuing against a destroy, not of the destroy-cost curve.

It does not fix `MAX_MONEY`. An uncapped ORU tail means the 10^10 ORU bound is a
deadline (year 1 485) rather than a bound. Raising it, or bounding cumulative
issuance, is separate work.

It does not resolve the early-liquidity question. RES issuance is 6 564 in year
1 and 102 616 through year 16. Thin early RES supply pins the secondary-market
RES/ORU ratio to the mint destroy-cost ceiling, which maximises the share of
RES demand transmitted into ORU — the intended effect — but a market that is
too thin to discover any RES/ORU ratio at all would prevent that transmission
from starting. This RFC asserts the mechanism, not the threshold.
