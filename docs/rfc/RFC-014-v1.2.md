# RFC-014 v1.2 — Amendment: `RES_PROBABILITY_TARGET` becomes a per-draw quantity

**Type:** AMENDMENT to `RFC-014-frozen-convergence-target.md` (v1.0), as already amended by `RFC-014-v1.1.md`
**Status:** PRE-MAINNET CORRECTION — not yet activated
**Raised by:** SECURITY-001-A8 design review, finding F-1; implemented as TASK-SECURITY-001-A9C
**Date:** 2026-08-04

> **This document does not rewrite history.** RFC-014 v1.0 and the v1.1 erratum both remain in
> the repository unmodified. Where the three conflict, **v1.2 governs the value and the
> interpretation of `RES_PROBABILITY_TARGET`; v1.1 governs the unit derivation it builds on;
> v1.0 governs everything else.**

> **Relationship to v1.1.** v1.1 fixed a *unit* error: the constant was being evaluated at a
> normalised weight while the implementation denominates weights in satoshis. v1.2 is not a
> defect correction in that sense. The constant v1.1 produced is arithmetically correct and
> remains the reference point; what changes is that the quantity it governs is no longer
> evaluated once per block but once per block **per candidate that is still inside a 32-block
> window**. Holding issuance fixed under that change requires dividing by the window width.

---

## 1. Summary

| | Value |
|---|---|
| **v1.1** | `RES_PROBABILITY_TARGET := floor(2^240 / MIN_CONVERGENCE_AMOUNT)` |
| **v1.2** | `RES_PROBABILITY_TARGET := floor(floor(2^240 / MIN_CONVERGENCE_AMOUNT) / CONVERGENCE_DRAW_WINDOW)`, `CONVERGENCE_DRAW_WINDOW = 32` |
| **Reason** | The candidate set F now spans 32 blocks, so each convergence transaction competes in 32 draws instead of one |
| **Effect on aggregate issuance** | **None by construction.** Expected wins per candidate is `W · p_draw(n) = n / 65536`, exactly the v1.1 figure |
| **Effect on per-draw eligibility** | Divided by 32. Per-draw saturation moves from 65536 ORU to 2,097,152 ORU |
| **Effect on the consensus rule form** | **None.** The rule remains `σ_i < T · f_i`; only `T` changes |
| **Effect on the σ construction** | **None.** Byte-for-byte identical, including field order and the deferred-draw timing |
| **Chain impact** | Chain-invalidating from height 1 |

## 2. Why the change is necessary

v1.1 closed a defect in the eligibility *filter*. It did not touch the eligibility *set*, and the
set was where the remaining problem lived.

Under RFC-010 as frozen, F is enumerated exclusively from the transaction list of block h-1. The
producer of that block therefore decides who is allowed to compete — unilaterally, at zero
marginal cost, and unfalsifiably, because no consensus rule can compel the inclusion of a
transaction a node cannot prove was ever offered. With `CONVERGENCE_DRAW_MIN_TXS_FOR_RES == 1`, a
single self-owned convergence transaction is a valid draw.

The consequence is not an attack but an equilibrium. Including a competitor's convergence
transaction means surrendering a 100 RES lottery ticket in exchange for a negligible fee, so not
censoring is a strictly dominated strategy. RES allocation converges to hashrate allocation, and
a censoring miner acquires RES at the **minimum** burn of 1 ORU rather than at the market burn
price — contradicting the project's position that proof-of-work does not directly generate RES.

## 3. The amendment

### 3.1 The candidate set

The draw resolved at height h enumerates F over blocks `[h-W, h-1]` rather than over block `h-1`
alone, with `W = CONVERGENCE_DRAW_WINDOW = 32`. The window slides by one block per height; it does
not tumble in epochs.

Widening the window does **not** reduce the share of F a large producer controls: with hashrate
share α he still produces roughly `αW` of the window. What it removes is **exclusivity**. The
candidates contributed by blocks `[h-W, h-2]` are already buried and cannot be withdrawn, so a
producer can no longer construct a draw in which he is the only entrant. He must outbid
candidates he cannot censor, which re-couples RES acquisition to burn.

### 3.2 Normative value

```
CONVERGENCE_DRAW_WINDOW      = 32
RES_PROBABILITY_TARGET       = floor(2^240 / MIN_CONVERGENCE_AMOUNT) / CONVERGENCE_DRAW_WINDOW
                             = 0x0000000000015798ee2308c39df9fb841a566d74f87a7a9a7aeb02c2d2f8e0d1
```

### 3.3 Choice of W

The binding constraint is the probability that a single producer supplies the **entire** window,
since that is the only condition under which exclusivity returns. For hashrate share α that
probability is `α^W`. Taking the design maximum as `α = 0.5` and requiring below `1e-9` gives
`W ≥ 30`; 32 is the next power of two, which makes the target a single shift of the v1.1 value and
`log2(W)` an integer.

| α | α^W at W = 32 |
|---|---|
| 0.25 | 5.4e-20 |
| 0.33 | 3.9e-16 |
| 0.50 | 2.3e-10 |

### 3.4 Issuance neutrality

A convergence transaction is now a candidate in W consecutive draws rather than one. Left alone
that would multiply issuance by W. Dividing the target by the same W restores neutrality:

```
per-draw probability      p_draw(n) = n / (65536 · W) = n / 2097152
expected wins per tx      W · p_draw(n) = n / 65536        (unchanged from v1.1)
```

Every aggregate figure in RFC-014 v1.0 §5.4 is therefore preserved, as it was under v1.1.

**The division is a floor, not exact.** The v1.1 target's residue mod 32 is 28, so the division
discards it. The resulting deviation from exact neutrality is a relative `28/T ≈ 1.6e-63`, below
the smallest quantity the protocol can express. The invariant pinned by test is consequently the
floor relation `T'·W ≤ T_v1.1 < (T'+1)·W`, not a lossless round trip. An earlier draft of the A-9-C
specification claimed exactness; that claim is withdrawn here.

### 3.5 Saturation softens — explicitly accepted

v1.1 §3.4 accepted saturation as a new property: at `f ≥ 65536 ORU` eligibility held
unconditionally. Under v1.2 that guarantee is gone. Per draw, saturation requires
`65536 · W = 2,097,152 ORU`; a candidate burning 65536 ORU is eligible in at least one draw of its
window with probability `1 - (1 - p/W)^W ≈ 1 - e^-1 ≈ 63%`.

This is intended rather than tolerated. The design review's finding F-2 identified "burn to
saturation, then censor" as the cheapest route to *guaranteed* RES acquisition, and removing the
guarantee is the point of the change. Expected wins per unit burned is unchanged, so the
burn-proportional fairness property v1.0 rests on is preserved; what is removed is the ability to
convert a large enough burn into certainty within a single block a miner controls.

### 3.6 One candidate, at most one payout

Because a candidate now survives in F for up to W draws, a rule is required to stop the same
convergence being paid more than once. A candidate is excluded from F if a RES mint anywhere in
the current window already named it.

The exclusion is applied at set construction, before C is computed. This keeps the draw a pure
function of the window: any validator holding the same W blocks derives the same F, the same C,
and the same winner, with no persisted state beyond the blocks themselves.

## 4. Scope

### 4.1 Amended

- `RES_PROBABILITY_TARGET`: value and interpretation (per-draw rather than per-block).
- RFC-010 §1 Step 1–3: F and C are enumerated over the window, not over block h-1.
- v1.1 §3.4: the saturation guarantee is replaced by the curve in §3.5 above.

### 4.2 Explicitly NOT amended

- The σ construction: `σ_i = Hash256(txid_i ‖ C ‖ B_{h-1} ‖ LE32(h))`, byte-for-byte, including
  field order and the 100-byte preimage layout.
- The deferred-draw timing established by SECURITY-001-A8: block h-1 commits, block h pays.
- The consensus rule form `σ_i < T · f_i` and the 512-bit cross-multiplication that evaluates it.
- The winner rule: argmin by cross-multiplication with a raw-byte txid tie-break.
- `MIN_CONVERGENCE_AMOUNT`, `RES_MAX_SUPPLY`, `RES_REWARD_AMOUNT`, and every ORU economic
  parameter.
- `CONVERGENCE_DRAW_MIN_TXS_FOR_RES`, which stays at 1. With exclusivity removed the threshold no
  longer protects anything.
- `CTxOut`, the transaction format, the block header, and script semantics. The window adds no
  consensus state and no new primitive.

### 4.3 New normative requirements

1. A validator that cannot read the full window MUST treat the draw as unavailable. It MUST NOT
   resolve over a shortened window, because that yields a different F, a different C, and a
   different winner — a fork whose cause is local disk state. Near genesis the window is
   legitimately shorter, and that case is complete rather than truncated.
2. C MUST be computed over the whole window. It is a σ input, so a validator that computed it
   per-block would compute different σ values for every candidate.
3. The live-view builder and the undo-replay builder MUST agree candidate-for-candidate under a
   window, including the no-double-win exclusion.

## 6. Downstream synchronisation

- `core/contrib/ops/closed-testnet/scripts/day0-smoke.sh` pins `T` and was updated.
- `formal_verification/rigor_golden_vectors.json`: `WIN-001` and `WIN-002` carried weights at the
  old saturation point specifically so that eligibility would be deterministic and the vectors
  would test winner *selection*. Their weights were raised above the new per-draw saturation point
  to preserve that intent. σ is unaffected, since the weight is not a σ input.
- `getconvergenceresult` now enumerates F itself rather than the source block's transactions, and
  reports `source_height` per candidate plus `window_size`, `window_first_height`, and
  `window_last_height`. Any consumer that recomputed the winner from the old candidate list would
  have disagreed with the node under a window.
- The `bad-convergence-window-reset` rule, together with `bad-last-res-hash` and
  `bad-convergence-window`, was removed. It required convergence to have accumulated since the
  last RES *mint*, which is a different window from the draw's; once consecutive draws share
  candidates it would reject valid blocks. See TASK-SECURITY-001-A9C §12.3.

## 7. Adjudication note

This amendment is narrower than it looks. It changes where candidates come from and rescales one
constant to keep issuance fixed. It does not touch the randomness construction that SECURITY-001-A8
established, add consensus state, introduce a primitive, or alter storage — the σ preimage is
unchanged to the byte, and the draw remains verifiable by any node holding the blocks.
