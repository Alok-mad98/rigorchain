# RFC-014 v1.1 — Erratum: unit correction to `RES_PROBABILITY_TARGET`

**Type:** ERRATUM / AMENDMENT to `RFC-014-frozen-convergence-target.md` (v1.0)
**Status:** PRE-MAINNET CORRECTION — not yet activated
**Raised by:** SECURITY-001-A finding A-6
**Date:** 2026-08-02

> **This document does not rewrite history.** RFC-014 v1.0 remains in the repository
> unmodified and remains the record of what was adjudicated and shipped. This erratum
> records a defect found in it, the correction, and the scope of that correction. Where the
> two conflict, **v1.1 governs the constant; v1.0 governs everything else.**

## 2. The defect

### 2.1 What v1.0 says

§2.1 defines the constant and immediately derives the per-input probability:

```
p_per_input  :=  RES_PROBABILITY_TARGET / 2^256
              =  2^{-16}
```

That division is only the probability of the §2.2 rule

```
H_i  <  RES_PROBABILITY_TARGET · f_i
```

**when `f_i = 1`.** §2.2 licenses exactly that reading by requiring `f_i >= 1` and citing
RFC-000 §7's "integer, ≥ 1".

### 2.2 What the implementation does

`f_i` is the convergence amount **in satoshis**, floored at
`MIN_CONVERGENCE_AMOUNT = 1 ORU = 10^8` satoshis. The smallest admissible weight is therefore
`10^8`, not `1` — the derivation and the implementation disagree by a factor of `10^8`.

RFC-000 §7's "≥ 1" is denomination-silent, and nothing in v1.0 pins it. That silence is the
root cause.

### 2.3 Consequence — the eligibility filter was vacuous

With `T = 2^240` and `f_min = 10^8`:

```
T · f_min / 2^256  =  1525.87890625
```

The right-hand side exceeded the entire 256-bit digest range by three orders of magnitude,
so `H_i < T · f_i` held for **every** candidate at **every** weight, unconditionally. The
eligibility filter was a constant `true`.

The consequences were not confined to probability:

1. Every convergence candidate in a block was eligible, so the draw reduced to
   `argmin H_i/f_i` over whatever set the block producer chose to include.
2. Combined with `CONVERGENCE_DRAW_MIN_TXS_FOR_RES = 1` (RFC-015), a block producer
   including exactly one self-authored convergence transaction won with probability 1.
3. The intended issuance law never operated. RES issuance was governed by miner behaviour,
   not by the constant — which is precisely the failure mode v1.0 §1 was written to prevent.

The 512-bit cross-multiplication of §2.3 was **not** at fault. It computed the stated
inequality correctly; the stated inequality was calibrated in the wrong units.

## 3. The correction

### 3.1 Normative value

```
RES_PROBABILITY_TARGET  :=  floor(2^240 / MIN_CONVERGENCE_AMOUNT)
                        =   floor(2^240 / 10^8)
                        =   0x00000000002af31dc4611873bf3f70834acdae9f0f4f534f5d60585a5f1c1a3c
                        =   17668470647783843295832975007429185158274838968756189581216062012
                            (decimal)
```

The floor discards a remainder of `92619776`, i.e. a relative error below `2^-183`. It is
irrelevant to the economics and is taken so the constant remains an exact integer with one
canonical encoding, as v1.0 §2.4 requires.

### 3.2 Probability interpretation

For a candidate converging `n` ORU (weight `f = n · 10^8` satoshis):

```
p(n)  =  min(1,  n / 65536)
```

| `n` (ORU) | `p(n)` | odds |
|-----------|--------|------|
| 1 | 1.52587890625·10⁻⁵ | 1 in 65 536 |
| 2 | 3.0517578125·10⁻⁵ | 1 in 32 768 |
| 10 | 1.525878906·10⁻⁴ | 1 in 6 553.6 |
| 100 | 1.5258789·10⁻³ | 1 in 655.4 |
| 65 536 and above | 1 | certain (saturated) |

`p(1 ORU) = 2^-16` **exactly**, which is the figure v1.0 §2.1 stated and §5.4 priced. The
correction restores the intended economics rather than replacing them.

### 3.3 Satoshi denomination — why the constant moved instead of the weight

Two repairs were available:

- **(a)** keep `T = 2^240` and redenominate `f_i` into whole ORU;
- **(b)** keep `f_i` in satoshis and divide `T` by `MIN_CONVERGENCE_AMOUNT`.

**(b) is adopted.** Under (a), a convergence of 1.5 ORU would have to be truncated to an
integer ORU weight, which discards value, breaks the exact-amount binding introduced by
SECURITY-001-A finding A-4, and creates a rounding boundary an adversary could grind against.
Under (b) the weight remains the exact on-chain satoshi amount and the arithmetic in §2.3 is
untouched. The winner comparison `H_i · f_j < H_j · f_i` is scale-invariant, so (a) and (b)
select the same winner among eligible candidates; they differ only in eligibility precision,
where (b) is strictly finer.

### 3.4 Saturation is a new, explicitly accepted property

Under the corrected law, any convergence of ≥ 65 536 ORU is eligible with certainty. This is
inherent to the linear form `p ∝ f` that v1.0 §2.2 already fixed, and was merely invisible
while the filter was vacuous. It is not a new privilege: eligibility is not victory, and
`argmin H/f` still decides the winner among all eligible candidates. Large converters buy
certainty of *entry*, not of *winning*.

## 4. Scope of this erratum

### 4.1 Amended

- **§2.1 "The constant"** — the numeric value only. The `p_per_input = 2^-16` figure is
  retained and is now correct as stated, at the reference weight of 1 ORU.

### 4.2 Explicitly NOT amended

| Section | Status |
|---------|--------|
| §2.2 the inequality | **UNCHANGED.** `H_i < T · f_i` is exactly as specified |
| §2.3 comparison rule | **UNCHANGED.** 512-bit cross-multiplication, no division, no floating point |
| §2.4 encoding canonicity | **UNCHANGED.** Still one `uint256` in `Consensus::Params`, still identical across all networks, still never `SetCompact` |
| §3 Sigma-CR-01 | **UNCHANGED.** σ derivation and `target_prev` binding untouched |
| §4 architectural declaration | **UNCHANGED.** PoW and RES issuance remain independent control systems |
| §5.4 economics | **UNCHANGED.** 100 RES/yr at N=125, 7.3% saturation at N=5000, 228-day cold start at N=2 all reproduce exactly |
| §6.2 pre-launch posture | **UNCHANGED and now binding** — see §6 below |
| §8 forbidden changes | **UNCHANGED** |

### 4.3 New normative requirement

> **§2.5 (new) — Non-vacuity invariant.**
> `RES_PROBABILITY_TARGET · MIN_CONVERGENCE_AMOUNT < 2^256` **MUST** hold.
> Violation makes the eligibility filter unconditionally true and voids the issuance law.
> Any future retune of `RES_PROBABILITY_TARGET` or `MIN_CONVERGENCE_AMOUNT` MUST re-check it.

This invariant is the one whose absence allowed the defect to ship. It is enforced in code by
`res_proof_math_tests.cpp::security001a_eligibility_filter_is_not_vacuous`.

## 6. Migration

**Chain data mined under `2^240` is unreplayable under v1.1.** The corrected constant changes
which candidates are admitted to the draw, so blocks containing RES mints that were valid
under the old rule are not valid under the new one. Those chains do not merely lose a
security property; they fail validation outright. Every existing regtest, devtest, and
closed-testnet database must be archived and discarded, not reused.

**Genesis blocks are not affected, and no new genesis needs to be minted.** This corrects an
earlier reading of v1.0 §6.2. A genesis hash is a function of the block header and its
coinbase — `nTime`, `nBits`, `nNonce`, `nVersion`, the timestamp payload, the output script,
and the initial subsidy. `RES_PROBABILITY_TARGET` is assigned to `Consensus::Params`
separately and never enters `CreateGenesisBlock`. All six hard-coded genesis asserts in
`core/src/kernel/chainparams.cpp` still hold after this amendment, and the C++ suite (which
constructs every chainparams object, executing those asserts) passes.

v1.0 §6.2's requirement that activation be **GENESIS-ONLY** is satisfied without minting new
genesis blocks: a chain restarted from the existing genesis has the corrected constant in
force from height 0, which is exactly what the activation gate requires. §6.1's prohibitions
on fork-height checks, versionbits, and dual-rule periods are likewise unaffected.

See `docs/migration/CHAIN_REGENERATION_POLICY.md`.

## 8. Adjudication note

v1.0 §1.2 records that `H-RES-PROBABILITY-FREEZE-001` and `H-RES-ARCHITECTURE-VERDICT-003`
found `2^240` "uniquely optimal". **Those verdicts stand.** They were reasoning about
`p(1 ORU) = 2^-16`, and that is exactly what v1.1 delivers. What failed was not the monetary
adjudication but its transcription into a consensus constant: the reviews validated a
probability and the code shipped a raw comparison threshold, and no one checked the units at
the boundary between them.

**This erratum is a unit correction, not a new monetary decision.** No new economic
adjudication is sought or implied.
